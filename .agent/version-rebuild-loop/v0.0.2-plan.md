# v0.0.2 Plan

Status: active version plan

## Purpose

Create a parallel kit-by-kit rebuild layer that uses `v0.0.1` only as validated reference and lessons.

## Architecture Rule

```txt
domain = broad system area
subdomain = focused capability inside that area
kit = one owned, testable unit inside a subdomain
```

## Version Scope

- Create top-level kits under `src/kits/v0.0.2/<domain>/<subdomain>/`.
- Use `src/kits/v0.0.2/registry.js` as the source of truth.
- Use grouped proof pages under `public/proof/v0.0.2/`.
- Expose a read-only `window.GoldRushHost.getState().v002` surface.
- Keep existing `engine.n.goldrush*` APIs intact during the scaffold phase.
- Treat FBX/OBJ/BLEND as source-only intake through the new content domain; promote GLB only after review and runtime-gate proof.

## Domains

- runtime
- scene
- world
- physics
- control
- behavior
- animation
- render
- gameplay
- network
- audio

- goldrush

## Boundary Rules

- Behavior kits are system controllers that decide intent from an outside perspective.
- Animation and narrow control kits are execution kits that apply descriptors.
- Render kits consume descriptors and never own gameplay truth.
- GoldRush kits compose reusable kits into game-specific rules and are not promotable as-is.
- Proof pages validate grouped domains, not one page per small kit.

## Slice Order

1. Registry, metadata, kit folders, grouped proof pages, validators, and `v002` state surface.
2. Source-only content intake for FBX/OBJ/BLEND provenance, inventory, and conversion requests.
3. Runtime and scene proof integration.
4. World/physics terrain source handoff from validated `v0.0.1` terrain contracts.
5. Control/behavior/animation controller split.
6. Render descriptors consuming kit snapshots.
7. Gameplay mine/carry/cashout loop.
8. Train/lobby/title sequence.
9. Match/results/replay.
10. Network staging and simulator proof.
11. Public proof refresh.
