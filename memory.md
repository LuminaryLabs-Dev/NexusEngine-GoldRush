# Repo Memory

## Purpose

`NexusEngine-GoldRush` is the destination repo for the modern Gold Rush rebuild. It should become a static-browser-deployable game backed by NexusRealtime-style kit composition and room orchestration.

## Architecture Decisions

- Keep this repo as the only local checkout for the Gold Rush rebuild workflow.
- Treat legacy repositories as cloud-side source inputs only.
- Raw legacy data must land in `raw/imported/<jobId>/`.
- Sanitation and conversion outputs must land in `sanitized/`.
- Runtime app assets must land in `public/assets/`.
- Approved legacy runtime metadata lives in `src/content/goldrushApprovedAssets.js` and overlays placeholder slots only after full provenance, hashes, approval id, and safe `assets/...` runtime paths validate.
- The active GPT/cloud legacy asset transfer packet is `manifests/import-jobs/goldrush-cloud-transfer-handoff.json`; it must validate before any raw import PR is treated as acceptable.
- Cloud-side raw asset/audio copies must now include the full receipt set in `docs/cloud-asset-receipts.md` and pass `tools/validation/validate-cloud-asset-receipts.mjs`. Before cloud import this gate must report `waiting-for-cloud-asset-receipts`; once any raw candidate or receipt appears, source discovery, deny scan, secret scan, copy ledger, hashes, and classification receipts are all mandatory. Import branches use strict receipt mode through `.github/workflows/validate-cloud-import.yml`.
- Cloud-side source access is now separately proven by `reports/provenance/goldrush-source-access-2026-06-29.json` and `tools/validation/validate-source-access-proof.mjs`. This proves `thecrimsondeveloper/Gold_Rush` branch `development` at `144230e32b537336c83407b4ddae83cdc95c1c9e`, both Unity roots, product names, Unity versions, and six required scene blobs without creating a local legacy clone. It is identity/access proof only, not a raw-copy receipt.
- The first safe cloud-copy slice is defined by `manifests/import-jobs/goldrush-cloud-first-copy-slice.json` and validated by `tools/validation/validate-cloud-first-copy-slice.mjs`. It turns the source proof into four bounded raw-copy domains: actual music/SFX, legacy scene layout metadata, player/combat character assets, and mine/town/terrain props. This manifest does not trigger the receipt gate or claim copy completion; it tells cloud workers what to copy first and what receipts must land with that raw copy.
- `tools/import-sanitize/generate-cloud-source-discovery.mjs` converts the source-access proof into the required cloud source-discovery receipt shape. By default it prints JSON to stdout; writing `reports/provenance/goldrush-dual-source-001-source-discovery.json` requires `--allow-receipt-write` so local pre-import validation does not accidentally trigger the partial-receipt gate.
- `tools/import-sanitize/generate-cloud-candidate-inventory.mjs` uses the GitHub tree API at the proven source commit to produce metadata-only candidate inventory in `reports/provenance/goldrush-dual-source-001-candidate-inventory.json`. This does not copy file contents and does not satisfy raw-copy receipts; it gives the cloud worker exact candidate blobs for the first-copy domains.
- `tools/import-sanitize/generate-cloud-raw-copy-plan.mjs` reduces the metadata inventory into `reports/provenance/goldrush-dual-source-001-raw-copy-plan.json`, a deterministic first raw-copy plan with selected target raw paths and explicit deferred slots. It remains metadata-only and requires the cloud worker to produce the six receipt files with actual raw copy.
- Game code should compose domain kits instead of hiding reusable behavior in renderer code.
- GoldRush uses a two-layer Domain Service Kit system: neutral generic incubator kits under `src/kits/generic-incubator/` install first with `n:*:*` domainPath metadata, then GoldRush custom kits connect them into game-specific rules.
- NexusRealtime/ProtoKits source-doc alignment is a validated gate: `manifests/source-docs/nexus-kit-source-alignment.json` anchors installed docs and package-lock commits, while `tools/validation/validate-nexus-source-alignment.mjs` proves local kit contracts, headless runtime install, ProtoKit construction, renderer boundaries, and ME ledger sync.
- GoldRush now loads the reusable ProtoKit route/cargo/extraction stack through `engine.n.goldrushProtoKitBridge`. The bridge hosts `generic-route-progress-kit`, `generic-resource-loop-kit`, `generic-pressure-loop-kit`, and `generic-route-cargo-extraction-kit` in an isolated NexusRealtime runtime because direct main-engine ticking currently overflows inside the imported composite stack. Live mining, damage, pressure, and cashout actions mirror into the bridge snapshot, while custom GoldRush extraction/scoring remains owned by `engine.n.goldrushExtractionLoop`, `engine.n.goldrushExtractionReceipts`, and `engine.n.goldrushScoring`.
- Legacy version selection is a secondary lobby foldout, not the hero room choice. `engine.n.goldrushLegacyModes` owns `modernExtraction`, `classicCombat`, and `classicSolo`; the browser flow launches all through the same train handoff and unified runtime, with combat modes allowed to force `cameraMode: combat` and `sceneState.currentSceneId: goldrush.scene.legacyGame`.
- Generic incubator kits are local promotion candidates only. They must not contain GoldRush naming, GoldRush rules, or asset-specific assumptions, and `tools/validation/validate-domain-kit-contracts.mjs` enforces that boundary.
- `engine.n.goldrushKitContracts` exposes the full generic-to-GoldRush pairing registry, the 10-field kit contract template, and runtime install graph proof.
- `engine.n.goldrushNetwork` is the public multiplayer contract. The old shard structure is now an internal 50-player partition policy behind that kit.
- Player joining UI is scoped to a small PeerJS party-code lobby: four players join by code, then the party leader launches the larger simulated match.
- Renderers own presentation only.
- Local Codex work may add or modify kits only inside `NexusEngine-GoldRush`; other kit repos are cloud/GPT-it inspection sources, not local edit targets.
- The visible Gold Rush terrain should be a massive procedural field made from many small tessellated patches, not a circular arena primitive.
- Towns, mountains, paths, gold zones, loading gates, and room patch windows are first-class world descriptors owned by `engine.n.goldrushWorld`.
- Terrain windows, town layouts, path networks, gold zones, loading gates, camera descriptors, audio state, and animation state should be exposed as dedicated NexusRealtime APIs rather than only nested world data.
- Browser validation can inspect `window.GoldRushHost.getState()` for scenario, world, terrain, town, path, gold-zone, loading-gate, audio, animation, and camera descriptors.
- Match lifecycle state is split into dedicated `engine.n.goldrushMatch`, `goldrushFinalRush`, `goldrushExtractionReceipts`, `goldrushRoomHandoffReceipts`, `goldrushScoring`, `goldrushResults`, and `goldrushReplaySummary` APIs.
- Legacy source intake state is exposed through `engine.n.goldrushLegacySources`, backed by `manifests/import-jobs/goldrush-legacy-source-intake.json`, and must remain browser-safe with no raw/quarantine path strings in runtime source.
- Scoring, result finalization, receipt application, and replay summaries are kit-owned. The renderer and HUD may only present snapshots.
- Agent perspective packets live in `.agent/perspectives/` and simulate role, audience, market, player, runtime, import, and release viewpoints before broad changes.
- Network partitions target 50 simulated players each, with multi-room orchestration for 2-100 player matches hidden behind `goldrushNetwork`.
- `createNetworkOrchestrator().createSession()` owns live incremental room allocation: player 51 creates partition 2, leaves compact active roster assignments back toward partition 1, and high-water partitions stay retained until match end.
- Because the repository is public, `raw/imported/` is runtime quarantine only, not secrecy quarantine. Legacy files must be pre-scanned cloud-side before any raw import branch is pushed.
- Cloud transfer work must prove source commit, both Unity roots, product names, scene evidence, deny-path scan, secret scan, copy ledger, hashes, conversion, provenance, and human review before promotion.
- Runtime code must never import or reference `raw/`, `quarantine/`, `sanitized/converted/`, legacy repo paths, Unity manifests, Photon/Fusion config, or plugin folders.
- Runtime approved asset paths must be browser-relative `assets/...` paths backed by files in `public/assets/`; `public/`, `raw/`, `sanitized/`, `quarantine/`, absolute paths, URLs, traversal, query strings, fragments, and path encoding tricks are invalid.
- Sanitized candidates are not enough for promotion. `reports/human-review/goldrush-dual-source-001-request.json` and `reports/license-provenance/goldrush-dual-source-001.json` must stay pending until explicit approval exists; `tools/validation/validate-review-packets.mjs` fails accidental filled approval ids, runtime paths, approved statuses, or public/runtime promotion flags.
- Individual object dressing should be generated as stable `goldrush.micro.*` descriptors in `src/content/goldrushObjectMicroKits.js`, then batched by the renderer with instanced meshes. This is the local path for building thousands of small object kits without hand-authoring thousands of files.
- Object micro-kits should use the `micro-taxonomy-v2` shape with kit id, archetype, role, biome, placement zone/cluster/anchor/avoid tags, visual batch metadata, transform, and debug provenance.
- Terrain patch descriptors remain the orchestration/data contract, but the visible terrain mesh should render as a continuous field so tessellation does not expose blue/debug seams.
- Sky/terrain blending must not use a visible dome primitive in front of the player; the sky should read as background atmosphere plus horizon blend.
- `engine.n.goldrushFrontierConditions` owns deterministic match-condition descriptors and resolved effects. Conditions expose active/upcoming rotation, planning modifiers, world/audio/lighting descriptors, and effects; scene flow shows the active condition before train boarding; first-sequence payloads carry the briefing into loading-yard; extraction loop consumes mining payout, extraction timer/value, and combat pressure effects; extraction receipts carry condition context; results and replay summarize condition-linked receipts, risk/value/combat scalars, ambience, and lighting key; audio consumes ambience/music/stinger effects; the procedural renderer consumes sky/fog/lighting effects.
- `engine.n.goldrushCamera` owns a deterministic 1,000-pose camera perspective catalog across 10 player-view families. The active camera is selected from this catalog and carries playability checks instead of being treated as one hardcoded screenshot angle.
- Gold Rush visual composition should be driven by world/environment understanding, not by matching one reference picture. Reference images provide object vocabulary only; environment-space descriptors own canyon basin, wash floor, ridge walls, mine shelf, town shelf, gold seam, and extraction sightline placement logic.
- Gold Rush iteration should use a live one-change playtest loop: Codex verifies or launches the debug URL, the user plays, the user reports exactly one thing to change, Codex implements that one change, validates, screenshots, and repeats.
- The lobby should read as a squad staging screen inspired by modern battle-royale lobby composition: central character/pedestal, four party slots, compact group-type dropdown, PeerJS party-code controls, and one leader-only launch action. The party lobby caps at 4 players, while the first leader-launched mass match starts at 20 players.
- Start-screen audio should avoid sustained humming oscillator beds. Use short plucked/tapped procedural cues until approved legacy audio is imported.
- Audio placement now mirrors the imported Unity evidence without promoting raw files: `MainMenu.unity` play-on-awake maps to `goldrush.audio.music.titleIntro`, `Game.unity`/`Game_SinglePlayer.unity` `MusicManager` maps to wandering/combat/boss music cues, and `Player.prefab` `shootAudioSource` maps to `goldrush.audio.sfx.revolverShot`. `src/audio/goldRushAudioManager.js` is the browser host adapter; it plays approved `assets/...` runtime audio when records exist and otherwise uses short procedural fallback cues while reporting pending approved runtime assets.
- Scene loading is split into explicit sites so each scene can mount different kit groups: `site.start`, `site.lobby-character`, `site.loading-yard`, and `site.gold-field`.
- Scene-site kit groups are runtime-visible through `createGoldRushSceneKitLoader()` activation receipts, `window.GoldRushHost.getState().sceneKitLoader`, and `loadedKitGroups`, so each scene can load a different kit stack through dynamic renderer imports.
- Results are a first-class scene site: `site.results` loads `goldrush-runtime`, `results-summary`, and `replay-summary`. Completed extractions finalize through `runtime.endMatch()` and the existing result/replay kits before the DOM presents placement, score, extracted gold, frontier condition, extraction contest severity, awards, and replay moments.
- The lobby character must be an actual Three.js character preview that spins in place on pointer drag, not a CSS/2D character.
- The party leader `Start` flow enters a loading-yard scene before the mass match. The local player can walk to the train, the train departs, and only then does the app hand off to the 20-player gold-field runtime.
- The opening title -> lobby -> loading-yard train -> 20-player run sequence is now owned by `src/scenes/goldRushFirstSequence.js`, with receipts, deterministic phases, handoff payload consumption, and `tools/validation/validate-first-sequence.mjs`.
- Loading-yard train motion is path-driven through `createTrainPathKit()` Bezier samples. The train must approach, open its door, lock the boarded player to the train anchor, then depart along the track; sideways linear train drift is invalid.
- Loading-yard readability is now staged through `goldrush-train-sequence-readout-v1` and `goldrush-train-boarding-cue-v1`: the first-sequence kit exposes current beat, next player action, cue text, readiness, and camera directive, while the renderer shows an in-world train-door cue when boarding is available.
- Loading-yard transition audio is semantic cue-state, not raw asset promotion. `src/audio/goldRushAudioManager.js` consumes `goldrush-train-sequence-readout-v1` and emits `goldrush-train-transition-audio-cues-v1` one-shots for arrival, door opening, boarding, party sync, and departure, using procedural/placeholder cue IDs until approved legacy audio is promoted. Each beat must keep a distinct fallback pattern (`train-arrival`, `train-door`, `train-board`, `train-wait`, `train-depart`) so train state remains readable without relying only on text or debug state.
- Public/deploy smoke proof must validate train boarding through natural camera-relative walking from the loading-yard spawn. `tools/proof/public-deploy-smoke.mjs` records `boardingPath.method: natural-walk-from-loading-yard-spawn` and must not fall back to `publicSmokePlaceAtTrainDoor`, so a broken human boarding path fails before Pages proof can pass.
- The train/title/run audio cue approval plan is now explicit and sanitized by default. `tools/import-sanitize/generate-audio-cue-approval-plan.mjs --write` writes `reports/audio-cue-approval/goldrush-train-title-audio-cue-plan.json`, mapping 9 cue targets to pending review candidates where possible and exposing missing train SFX slots for `goldrush.audio.sfx.goldPickup` and `goldrush.audio.sfx.ambush`. `tools/validation/validate-audio-cue-approval-plan.mjs` is in `npm run validate` and proves the plan has 15 unique pending candidates, 0 approved candidates, no runtime paths, no public/runtime promotion, and distinct train fallback patterns.
- Loading-yard train boarding is now manifest-owned under `goldrush-train-boarding-v1`: `src/scenes/goldRushFirstSequence.js` records party seats, local boarding, auto-followed party members, party-ready receipts, and only starts departure after local boarding plus full manifest readiness.
- PeerJS party boarding sync is now exposed as `goldrush-peer-party-boarding-sync-v1` from `src/network/peerPartyRoom.js`. It fans out each browser's local boarding report and counts readiness only from per-peer local-boarded reports, preserving the rule that PeerJS is transport/fanout while first-sequence receipts own handoff authority.
- The live PeerJS boarding proof is `npm run proof:peer-party-boarding`; it opens host/member browser contexts, creates and joins a party code, launches loading yard, boards both clients, and verifies both snapshots show `goldrush-peer-party-boarding-sync-v1` at `2/2` ready. Latest proof report is `output/playwright/peer-party-boarding-proof/peer-party-boarding-2026-06-30T15-28-24-066Z.json`.
- Train handoff is now peer-gated for multi-member parties through `goldrush-peer-handoff-gate-v1`. `src/scenes/goldRushFirstSequence.js` locks the local player to the train after local boarding, stays in `boarding-syncing` while peer readiness is incomplete, and only starts departure/handoff after the PeerJS readiness snapshot reports all party members locally boarded. Latest gated proof report is `output/playwright/peer-party-gated-handoff-proof/peer-party-boarding-2026-06-30T15-35-13-986Z.json`.
- Loading-yard peer disconnects use `reduce-roster-require-remaining`: `src/network/peerPartyRoom.js` removes leaving/closed peers from the active boarding roster, records disconnect receipts, ignores stale reports from removed member ids, and forces the remaining local boarding report to republish so `goldrush-peer-handoff-gate-v1` can release only when the remaining roster is ready. Latest disconnect proof is `output/playwright/peer-party-disconnect-proof/peer-party-boarding-2026-06-30T15-57-04-607Z.json`.
- Terrain height/color math, tessellation bands, and downward raycast placement are owned by `src/physics/terrainCollider.js`. Renderers import them, movement samples them, and duplicate renderer-local terrain algorithms are invalid.
- The current terrain collider is a sampled heightfield descriptor with a real `cannon-es` adapter in `src/physics/cannonTerrainPhysics.js`; local movement uses `raycastTerrainDown()` plus `sampleTerrainCollider()` for grounding, slope checks, step-up limits, and central mountain blockers. `src/physics/physicsBackendKit.js` records the active decision: keep `cannon-es` for the current static-heightfield slice and add Rapier later behind the same public physics API for capsule/kinematic character control.
- Near-play terrain is the upper visible/collidable band where tessellation bands overlap, so player footing uses the detailed local surface instead of the coarse far-horizon triangles.
- Terrain render continuity is validated by `tools/validation/validate-terrain-continuity.mjs`. The blue/debug-looking terrain gaps were caused by downward-wound visible terrain triangles; `createBandedTriangleTerrainGeometry()` now winds top faces upward, carves coarse terrain band top faces beneath finer bands, adds band continuity metadata, and skirts exposed band edges without changing the collider/raycast contract.
- Central mountain readability uses split ownership: the collider heightfield keeps the real blocker lift, while visible mountain meshes mount to `terrainFieldBaseHeight()` so the renderer does not stack landmark geometry on top of the invisible collider summit.
- Run-scene and loading-yard movement are mouse-look driven: `localPlayer.look.yaw` controls the over-the-shoulder camera, and WASD movement is relative to that camera yaw.
- Runtime camera motion has a single authority: player-follow plus transition-latched camera descriptors. The 1,000-pose camera catalog is for proof/selection, but `goldrushCamera` must not choose a new `threeDescriptor` from `engine.clock.frame` every tick because that creates back/forth camera motion conflicting with mouse-look follow.
- Camera/ground stability is now a proofed player-facing contract. `npm run proof:camera-ground-stability` enters the match through natural train boarding, samples at least 120 run frames, and rejects camera perspective reselection, motion-authority changes, player/ground mismatch, render-ground mismatch, large camera jumps, large terrain-ground pulses, inactive mouse-look, and inactive camera-relative WASD.
- Extraction-loop combat presentation now syncs through one runtime boundary: active readable threats, aim, fire, and damage set `goldrushPerspective` and `goldrushCamera` to combat; clearing active threats returns camera, animation posture, and scene intent to exploration. Raw extraction/frontier risk can affect music/scoring, but cannot hold the camera in combat without an active threat.
- `engine.n.goldrushExtractionLoop` owns the local playable mining/carry/extract slice. It is the authority for mining progress, local combat pressure, extraction progress, final receipt, and world-space marker descriptors; the renderer only presents those descriptors.
- Mining claim pressure is now a first-class extraction-loop contract under `n:goldrush:mine-hold-action`. `goldrush-mining-claim-pressure-v1` exposes site quality, reward preview, hold progress, depletion, noise radius, claim heat, next risk, and deterministic mining receipts; world-space mining markers carry site-level readability data for future dust/audio/UI presentation.
- Contested extraction-site behavior is owned by `engine.n.goldrushExtractionLoop` under `n:goldrush:cashout-sites`: active frontier condition risk, cargo, and extraction progress produce `contestState`, expanded threat radius, linked threat calls, marker status, and `extractionSiteContest` receipt context.
- Readable local threat behavior is owned by `engine.n.goldrushExtractionLoop` under `n:goldrush:ambush-pressure`: active threats expose deterministic telegraphs, multisensory cues, danger lanes, cover descriptors, recommended cover ids, cover engagement/peek state, mitigation receipts, counterplay tags, and combat receipts. Renderer code consumes `extractionLoop.worldSpaceMarkers[*].telegraph/lane/cover/cue/engagedCoverId` and draws `readable-threat-lanes-v1` plus `readable-threat-cover-v1` under `goldrush.procGameplay.extractionLoopMarkers`; proof runs through `npm run proof:threat-lanes`.
- Threat audio is a host-audio adapter over the same readable threat contract: `src/audio/goldRushAudioManager.js` emits deduped `readable-threat-audio-cues-v1` one-shots from `extractionLoop.combat.readability.threats[*].telegraph.multisensory.audio`, currently mapped to the placeholder `goldrush.audio.sfx.ambush` slot until approved legacy SFX promotion.
- Results and replay consume extraction-loop combat receipts through `goldrush-combat-outcome-summary-v1`, preserving receipt counts, damage taken/dealt, threat lane IDs, telegraph IDs, under-fire awards, and combat replay moments without moving combat calculations into the DOM.
- Browser proof for combat results lives in `tools/proof/combat-results-proof.mjs` and runs through `npm run proof:combat-results`; it forces shot/damage receipts, extracts, enters results, and verifies visible Combat, under-fire award, readable `Claim Jumper` replay context, no raw threat/lane IDs in visible copy, and the result-state combat contract.
- Final-rush pressure is now part of the playable extraction loop: mining sites carry real gold-zone/window ids, `engine.n.goldrushExtractionLoop` exposes `goldrush-final-rush-extraction-pressure-v1`, cashout contests preserve final-rush pressure context, and accepted receipts use the real `gold.zone.*` id so `engine.n.goldrushFinalRush` pressure multipliers affect scoring.
- Result/replay summaries now explain final-rush scoring pressure through `goldrush-final-rush-result-summary-v1`: pressure-linked receipt count, highest/average pressure, max multiplier, pressured gold-zone ids, readable result text, replay moment pressure, and the `award.collapse-cashout` award.
- Player grounding is movement-owned: `createMovementController()` samples the terrain once for the player frame and exposes `localPlayer.renderGround`. Renderers should consume that cached render-ground height instead of recomputing local player Y from presentation terrain.
- Character walk animation should not pulse the whole player root vertically. Root height stays grounded; readable motion belongs in limb rigs, knees, boots, torso sway, camera response, or authored animation clips.
- Loading-yard boarding should be forgiving along the rail/platform approach, not a single tiny trigger circle, so normal walking and automated proof captures can reliably reach the train handoff.
- Public deploy readiness is not proven by `npm run check` alone. The Build deploy workflow runs `npm run proof:public` after GitHub Pages publishes, and that proof must validate the public URL through title, lobby, loading-yard train boarding, and the 20-player gold-field run scene.
- Public smoke proof URLs carry a `publicSmoke` query param. The app exposes a query-gated train-door placement action only for that proof so CI can validate train boarding/departure without depending on unreliable headless keyboard focus.
- NexusSimulator testing is wrapped locally by `tools/simulator/goldrush-nexus-sim.mjs`, which discovers `<github>/NexusSimulator/NexusSimulator-V1`, generates ignored `.nexus-simulator/` env/scenario state, starts Vite, and runs the external `nexus-sim` CLI with `--simtime nexusrealtime`. The app exposes `window.GameHost` as a compatibility bridge for simulator runs while keeping `window.GoldRushHost` as the main debug API.
- Shareable test output is sanitized by default. Agent packets, live-test reports, public smoke reports, Playwright `output` JSON, manifests, retained proof markdown/JSON, and all NexusSimulator CLI output should emit repo-relative artifact paths or external path labels such as `<github>/...`, `<documents>/...`, or `<tmp>/...`; absolute home/temp/browser-profile paths are allowed only for internal writes. `tools/safety/publicArtifactSanitizer.mjs` owns the shared sanitizer, its sanitized writer helpers are the default persisted-report boundary, and it also redacts standalone account emails, browser profile details, file URLs, token-like values, and secret query-string values. `tools/validation/validate-report-secrets.mjs` enforces the public-artifact leak gate across `.agent`, docs, manifests, output, and reports.
- Proof, simulator, and selected playtest tooling now have a static sanitizer-boundary gate. `tools/validation/validate-sanitized-artifact-boundaries.mjs` fails proof scripts that bypass `writeSanitizedJsonArtifact`, `sanitizedConsoleJson`, or screenshot path sanitization, fails the live playtest doctor if it prints raw JSON, and still allows ignored `.nexus-simulator/` internal state writes.
- Approval decision application stays sanitized and preflight-only by default. `tools/validation/validate-approval-decision-approved-fixture.mjs` creates and removes a temporary decision packet fixture, proves 1 approved-ready item with 736 pending decisions, routes to `approved-runtime-promotion-planner`, forbids runtime paths, and keeps public/runtime promotion false.
